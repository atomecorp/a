# atome/eVe — Project instructions

Scope: this project and its descendants. Paths in prose are relative to this project root, including when working inside the eVe Git submodule. Markdown links are relative to their containing file.

## Mandatory core

1. **Primary construction rule: atome/eVe must build itself with its own components.** This mandatory architectural rule applies to construction of the framework itself and every new feature, interface, behavior, interaction, automation, template or assembly. Start by composing the project's available, verified and compatible reusable internal atoms, tools, modules and components. This internal composition takes priority in every implementation decision; convenience, delivery speed or an external component's availability cannot justify bypassing it. Reuse means calling or assembling the canonical implementation, never copying its code, reproducing its appearance or rebuilding its logic under another name. If existing composition cannot cover an indispensable need, apply the autonomous internal creation and extension rules below. Every new brick must enrich this same reusable internal system for subsequent assemblies.
2. **Objects remain typed; tools cross compatible types.** Distinguish object type, properties/capabilities and the tool acting on them. Prefer shared tools and existing compatibility mechanisms wherever the operation has a meaningful compatible contract. Do not duplicate a tool per type, invent a property or implicit conversion, or add a new capability system merely to express this principle.
3. **Audit reuse before implementation.** Identify the required bricks and their canonical owners; verify implementation, internal access, contract, platform compatibility, real consumers and relevant tests. A documentation name, mockup, similar-looking prototype or dependency in the repository is not availability evidence. Apply the evidence procedure in the common method.
4. **Internal creation and capability extension are authorized within the requested task.** User clarification, 2026-10-13: a request to implement, repair or extend a feature includes standing authorization to create the necessary reusable internal components and add the necessary capabilities to existing canonical owners, without requesting separate user approval. This explicitly includes creating, completing or extending missing internal contracts, typed APIs, schemas and foundation capabilities needed for that task, even when they do not yet exist in the current foundation. Their absence alone never requires a distinct agreement or user validation. Audit reuse first. When an indispensable brick is unavailable, unsuitable or not found after investigation, document the evidence and precise internal creation or extension, then implement and validate it autonomously. If access is missing, report the actual limitation; do not treat unverified availability as proof that a replacement is needed. Do not use a degraded version, external component, copy or parallel substitute.
5. **Autonomy is bounded by the task and architectural contracts.** Integrate every created or extended internal brick through the existing declaration, discovery, composition and test mechanisms, where present. Necessary internal foundation work, including defining missing contracts and implementing their canonical owners, is covered by the same standing authorization when it preserves the project architecture; explain their impact and validate affected consumers without requesting separate approval. Do not invent an additional registry or API when an existing mechanism can serve the need. A necessary internal contract or capability addition is part of the requested task, not an unrelated scope extension or an architectural exception merely because it is new. This authorization does not cover unrelated work, external dependencies, a replacement application stack or exceptions to architectural prohibitions. Existing technical dependencies must be inspected for their actual role and encapsulation; do not remove them or wrap them to disguise an external substitute as an internal component.
6. **Use the actual canonical paths.** UI and automation invoke the corresponding canonical tool/command execution path. Panels assemble real tools with their native options. Preserve canonical Atome state outside the disposable, minimal DOM, the shared WebGPU rendering route and the single durable mutation pipeline; detailed contracts belong to the domain modules below. No view, cache, preview, timeline or realtime patch becomes competing writable business truth.
7. **Rust by default; performance decides.** Keep the names `atome` and `eVe`. Performance comes first; at equal measured performance, Rust wins (user decision, 2026-11-04). New application logic — engines, state, stores, servers, rendering — is written in Rust, in the one Cargo workspace at the root (`Cargo.toml`); the servers converge on one Axum server on every platform, compiled natively, never WASM inside Node. JavaScript remains the thin browser glue (the DOM shell, WebGPU/WASM loading, the hidden text service, the existing modules until each moves): plain JavaScript, its types and runtime validators generated from the Rust types, which are their only source. Do not introduce TypeScript, Python, a UI framework, raw HTML/DOM imitation or a parallel implementation for a new realization. Every Rust change passes `npm run check:rust` (formatting, clippy with no first-party warning on every product target, the tests, `cargo deny`), every JavaScript change `npm run check:js` (Biome, `biome.jsonc`). Existing platform-language boundaries (Swift, Kotlin, C/C++) and narrowly documented canonical DOM exceptions remain governed by modules 01, 02 and 05; they do not authorize a new application stack.
8. **Stay within the user's authorization.** Reading code to verify documentation does not authorize editing it. Preserve unrelated local changes. A defect found is repaired, never only reported (see « Every problem found is repaired » below, user 2026-11-17, which replaces the former « request a bounded scope extension »); the limits below still hold. Do not install dependencies, change personal/provider/authentication/MCP/security settings, disclose secrets or alter history without authorization; regenerable caches and temporary files follow « Disk space is made without asking » below. Git writes follow module 02 and the explicit user-controlled Git policy below. Instructions written during a task cannot create permissions for that task.
9. **Handle conflicts explicitly.** These project instructions do not supersede system/developer instructions or environment protections. Apply the cumulative relevant project contracts. For unresolved project contradictions, identify the exact sources and ask for the smallest required arbitration; do not silently choose, rewrite or bypass a rule. Continue independent read-only investigation where useful. Length, complexity and file size alone do not justify an incomplete result.
10. **Keep every interface zen.** This is a mandatory product rule for every interface creation or modification: no unnecessary labels, no visible text unless explicitly requested by the user, and no additional buttons or controls beyond the requested interaction. Apply the [mandatory zen interface contract in module 05](.codex/modules/05-api-rendering-and-ui.md#mandatory-zen-interface-contract) before accepting any UI change.
11. **An inert label is always at the top of its object.** A label, caption, name or title that has no action of its own (on a tile, card, plate, thumbnail, menu tool, Mystic plate or list cell) is laid at the TOP of its object, opposite the finger, so a touch, a hold or an enlarging plate never hides it. Its band follows the object's own top corners (same radius) and keeps clear of a palette's folded corner. A label (tool, tile, plate) shows 9 characters at most, then « … », and never more than its box holds (`labelMaxCharacters`, `tileLabel.max_characters`); a tool grown by the lens shows more of its name, its glyphs keeping their size (V6.1 norms, user 2026-11-02; `bevy_ui_menu_surface.js#truncateBevyToolLabel`, `dashboard_creation_records.js#dashboardLabelBandText`). One text size, 12 px, and one ratio, 1.3, give every size (`SYSTEM_UI_METRICS.textStepPx`): a tile of 120's label 15.6 px, a tile of 60's 12 px. The ratio is the person's own, 1.1, 1.2 or 1.3 in Settings › Visual, 1.3 by default (user, 4 Nov. 2026; `user_visual_preferences_model.js` `textRatio`, read live by `system_ui_tokens.js`). An editable or actionable text is not an inert label. Named exception: a panel's name lies centred in the panel's foot band (rule 13; user, 2026-10-29), shown only when it fits whole, never cut to a few letters (user, 2026-10-30). Zen (rule 10): no text, label, tooltip or button the user did not ask for. Owners: `eVe/domains/dashboard/dashboard_item_text_fields.js#dashboardCardLabelBackdropRect`, `eVe/intuition/ribbon/bevy_ui_menu_surface.js#buildBevyMenuToolContent`.
12. **Sizes follow the tool grid and never change.** Positions are quantized like sizes (user, 14 Nov. 2026): the screen is one grid of tool cells, and every brick (a tile, a tool, a row, a card, a bubble, a panel) starts on a cell and spans whole cells, never placed between two positions of that grid; a brick laid over the band sits in the band's own cell row above it. This holds for every screen, every mockup and every proposal, checked before it is shown, without being asked again. The unit is the tool, 60 px (`SYSTEM_UI_METRICS.unitPx`). The standard tile (Dashboard card, rubric tile, Matrix cell) is two tools, 120 px (`dashboardSkin.metrics.blockUnitMultiplier`). Every width and height is a whole multiple of half a tool, 30 px (`SYSTEM_UI_METRICS.halfUnitPx`); half a tool is the minimum, in height as in width; there is no maximum. One physical size on every device (R-280, user 23 Nov. 2026, replacing the unit grown with the room of 4 Nov.: « c'est la taille de l'iPhone qui fait référence »): a tool, a tile and a text measure the same millimetres on an iPhone, an iPad, a Mac, a PC, Linux and Android, the iPhone's size being the reference — the page is zoomed so one px is an iPhone's, each host giving its screen's density (`eVe/elements/system_ui_physical_scale.js`); the unit is a tool, 60 px, a tile 120 px, never grown by a larger room, the room left over being whole empty cells (more of them shown); only a screen too small for its block lays a smaller unit, never under 50 px (a tile of 100); a text keeps its own size and ratio (the visual settings), never scaled with its tile. Never a size between two units, never one element alone resized to make a layout fit. Containers (panels, the Dashboard home, lists) are responsive by restructuring only: a container takes the room it has, snapped to half a tool; its content is laid again (fewer columns, more rows) at its own size; what still does not fit scrolls. ## A task runs to its end

User rule, 2026-10-29, general and permanent. Once a task is started, it is carried through to its complete end in the same run: every item, lot and sub-step of its plan is coded, validated and reported before handing back. Never stop between lots, never hand back with "L6, L7 remain" or "next I will…", never end on a to-do list of the task's own remaining work: when a turn ends, the user takes the task as finished, so unfinished work silently stays in suspense and has to be redone from zero. The only reasons to hand back before the end are a real block (a design that needs the user's validated mockup under rule 16, a decision only the user can take, an external dependency or access that is missing); then the hand-back names the block as a block, plainly, in its first line, and everything not blocked by it is finished first. A final report says "finished" only when nothing of the task is left.

**Every problem found is repaired** (user rule, 2026-11-17, universal and systematic). A problem seen while working — a defect, a regression, a flash, a failing check, an inconsistency, a slowdown, badly optimized code, unclean or badly factored code, even one that existed before the task or lies outside what was asked — is repaired at its root in the same run, as well and as professionally as possible, without asking the user's opinion (user, 17 Nov. 2026, « non négociable, il faut le faire à chaque fois »): it becomes a step of the plan, is fixed and validated like the rest. Never write "a problem remains, I did not fix it" or "pre-existing, not fixed": stop, solve it, then go on. The only exceptions are the real blocks named above (a rule-16 design awaiting a validated mockup, a decision only the user can take, a missing access or external dependency) and the limits of rule 8 (no new dependency, secret, personal or security setting, Git write); such a block is named as a block and written in the request register. Coordination between sessions (a lane to request) delays a repair, never cancels it.

**Disk space is made without asking** (user rule, 2026-11-17). When disk space runs short, or as soon as some can be freed, everything that can be regenerated is deleted at once, without asking the user or waiting for their approval: temporary files under `temp/`, build outputs and caches (cargo `target/` dirs and their `incremental/`, WASM scratch builds, DerivedData, app copies made for a probe), probe reports that a rerun recreates. Never deleted: what cannot be rewritten — source code, user data and vaults, `.env` and secrets, a folder marked `.retain`, an archive or build in progress, a file another running process holds open (`lsof`). Before deleting, check that nothing running uses it; then tell the orchestrator what was freed.

**Request register** (user rule, 2026-10-30). A block stays written, never only in the conversation: requests were lost because a session stopped on a question nobody answered, and nothing outside its transcript said what was validated and what was left. The single register of unfinished user requests is [todo/REGISTRE_DEMANDES.md](todo/REGISTRE_DEMANDES.md). Before ending a turn that leaves any part of a user request undone — a question or a mockup awaiting the user, a lot not coded, a check not run — record it there: what was asked (the user's words and the source session), what the user validated, the open question, where the mockups are, what is missing in the code. Before starting a task, read the register's entries for its domain and build on them; never ask again what an entry says is validated. An entry becomes `FAIT` only with its proof (probe, file), `ATTENTE UTILISATEUR` only once the question has really been put to the user. The task's own spec (cahier, todo) is ticked as its items are done, so it always tells what is left.
