# Android release generator — Google Play internal testing

`scripts/Android_testflight_generator` is the Android counterpart of
`scripts/XCode_testflight_generator`. The distribution service is **Google Play
internal testing** (French Console: **Tests internes**). Authorized testers opt in
with their Google account, install from the Play Store and receive subsequent
updates there. This is separate from Firebase App Distribution and Internal App
Sharing. The generator only publishes to the `internal` track.

## Commands

Run from the repository root; the launcher also resolves paths from another cwd.

```sh
./scripts/Android_testflight_generator --help
./scripts/Android_testflight_generator --dry-run
./scripts/Android_testflight_generator --prepare
./scripts/Android_testflight_generator --doctor
./scripts/Android_testflight_generator
```

The equivalent canonical entry is `./run.sh apk --play-internal` with the same
options. `--dry-run` performs local planning only: no version reservation, file
writes, credential contents read, Google request, build, key creation or upload.
`--doctor` checks the installed build chain and reports missing Google setup; an
incomplete setup returns a nonzero exit status. Neither mode authenticates Google.

`--prepare` requires no Google account. It reserves an Android version code, calls
the existing `apk.sh --prod --aab --no-install-deps` build once, validates the actual
signed bundle, and retains an immutable copy plus `report.json` under a unique
`temp/android-release-*` directory. It never contacts Google. The final output gives
the exact AAB path, SHA-256 and public upload-certificate fingerprint.

Without `--prepare`, an explicit invocation performs the same build and publishes
it after checking Google configuration and remote versions. It stops before build
or version reservation when Google setup is missing. No account name is embedded
in the framework. No toolchain bootstrap, SDK licence acceptance, credential
creation, replacement signing key, tester invitation or production release occurs.
The build can resolve already-declared Cargo/Gradle dependencies through its normal
caches and repositories; no additional dependency is introduced by the generator.

## One-time Google setup

1. Open [Play Console](https://play.google.com/console/) with the intended owner.
   An ordinary Gmail account alone is insufficient: the Play developer account
   must be registered and verified. If registration is needed, the owner completes
   Google's payment, identity and any organization/device verification in Google's
   secure UI. The generator cannot perform legal consent or identity verification.
2. Select the existing app, or create the intended eVe app. The current release
   package is `com.squirrel.desktop`; `.debug` is a separate local test app.
   **Confirm this package before the first upload**: Google fixes it when the
   first artifact is uploaded. Do not substitute a different identifier to bypass
   a signing or account problem.
3. Produce the first bundle using `--prepare`. For an app already registered with
   Play, first obtain its expected **upload certificate** from Console and put it
   in the configuration below; preparation then checks it against the existing
   local key. An existing local keystore is reused, never regenerated by this lane.
4. In Console, open **Test and release → Testing → Internal testing**
   (**Tester et publier → Tests → Tests internes**). Create a release, upload the
   exact prepared AAB, configure **Play App Signing**, complete the required
   declarations accurately and roll out to the internal track. The initial upload
   must use Console before the Publishing API can manage the app.
5. Distinguish the **upload key** (local AAB signing key) from the **app signing
   key** (Google's certificate on APKs delivered to testers). Compare the configured
   upload fingerprint with Console's upload certificate. Retain an encrypted backup
   of the existing `~/.atome/android/squirrel-release.jks` and its credentials;
   never put these in Git. The generator only reads the existing key/properties.
6. In **Internal testing → Testers**, create/select the Google-address list, add the
   first testers, set the feedback address/URL, save and copy the opt-in link.
   Internal testing supports up to 100 testers. Testers must open the link with an
   invited account, join the test, then install from the Play Store. Initial links
   and updates can take time to appear; Console/API acceptance alone does not prove
   that a phone can install the release.
7. In [Google Cloud Console](https://console.cloud.google.com/), select/create the
   intended project, enable **Google Play Developer API / Android Publisher**, and
   create a dedicated service account. In **Play Console → Users and permissions**,
   invite its service-account address and grant access to this app with the rights
   to view app information and release to **testing tracks**. Do not grant production
   release or administrator rights. Google may group multiple testing tracks in one
   permission; the client additionally pins every track write to `internal`.
8. Configure the service account credential on this Mac, outside the checkout when
   possible. A private, ignored `Private/` path is also accepted. The credential file
   must have mode `600`, contain a Google `service_account` identity and use the
   official OAuth token endpoint. The scope is `androidpublisher`. Never paste the
   JSON key, passwords, access tokens or 2FA codes into chat. The file path is enough.
   This local implementation uses a service-account key; federation is not implemented.

## Local configuration

Copy the **nonsecret** example `scripts/android/play.config.example.json` to
`Private/android-play.json` and fill it after Console setup:

```json
{
  "packageName": "com.squirrel.desktop",
  "track": "internal",
  "serviceAccountFile": "/absolute/private/path/google-play-service-account.json",
  "uploadCertificateSha256": "64_HEXADECIMAL_DIGITS_FROM_THE_UPLOAD_CERTIFICATE",
  "initialUploadComplete": true,
  "testerOptInUrl": "https://play.google.com/apps/testing/com.squirrel.desktop",
  "releaseNotes": [
    { "language": "fr-FR", "text": "Description of this test release." }
  ]
}
```

The placeholder fingerprint above is intentionally invalid. Use the real public
fingerprint from the verified preparation output and match it to Console.
`initialUploadComplete` is the owner's confirmation that first Console upload,
App Signing and internal-track setup are complete; it is not inferred from a login.
Optional release notes contain at most 500 characters per language. The opt-in URL
is recorded only; the script never sends messages or invitations to testers.

Use `--config /absolute/path/android-play.json` or `ATOME_PLAY_CONFIG` to select a
different configuration. Configuration fields are strictly validated; neither a
production-track option nor an arbitrary provider URL is accepted.

## Versioning, reports and recovery

`atome/version.txt` supplies the displayed semantic version (`1.19` becomes
`1.19.0` for Tauri). The generator does not rewrite atome/eVe product versions or
iOS release settings. Android's canonical
`platforms/desktop-tauri/tauri.android.conf.json` stores the version-code high-water
mark. A live release selects a code greater than that mark and every returned
Play track/APK/AAB code. `--version-code N` can explicitly choose a greater code,
including during offline first preparation. It cannot reuse a consumed code.

The code is reserved **before** build and remains consumed after failure. This
prevents accidentally reusing a code after an upload whose response was lost.
No Git stage, commit, fetch or push is performed; the version/configuration and
source changes remain for the user to commit. Preserve the high-water mark when
synchronizing this checkout with other release machines. Play remains the remote
authority; concurrent uploads from another machine can still cause rejection.

To revalidate and publish/resume one exact prepared release without building again:

```sh
./scripts/Android_testflight_generator --publish /absolute/path/to/temp/android-release-ID/report.json
```

Reports bind the package, version, signed AAB path, SHA-256, certificate, validation
results, edit identifier, operation checkpoints and known Google result. They
contain no OAuth tokens or private-key contents. Do not delete a release directory
while its preparation, publication or recovery is in progress. Changing its AAB
causes verification failure. Do not edit report checkpoints to force an upload.

Only reads retry bounded 429/5xx/network failures. Upload and commit are never
blindly repeated. Explicit recovery inspects the original edit/remote bundle;
matching committed versions are confirmed without another upload. An older
report cannot replace a newer Play version; it requires a new build/code. An uncertain
upload absent from its original/renewed edit stops and instructs the owner to
inspect Console or prepare a higher code. A concurrent Console edit or expired
edit is reported; it is not silently overwritten. `ERROR_IF_IN_REVIEW` prevents
the commit from cancelling an existing Google review.

A successful commit is read back through a fresh edit before the script says
**GOOGLE PLAY INTERNAL COMMIT CONFIRMED**. The final phone installation remains a
separate acceptance step. If commit succeeds but confirmation fails, retain the
report and resume it rather than assuming either success or failure.

The release lock is `temp/android-play.lock` (contains the owning PID); the shared
build lock is `temp/android-build.lock`. Normal exits release them. After an abrupt
process kill, verify that the owning process/build is stopped before removing a
stale lock. Never remove a lock held by an active release.

The Tauri build coordinates Gradle/native compilation through its own temporary
loopback WebSocket. A sandbox denial at that stage (`failed to build WebSocket
server: Operation not permitted`) requires authorized local execution with access
to that listener and the existing build caches; it is not a Google login failure.
Do not modify a running shell script while a long build is using it. Stabilize
the source first, then rerun the generator after a failed attempt.

## Validation and acceptance

The canonical Tauri build provides the exact artifact path. There is no search
for an older bundle. `bundletool` comes from the **existing AGP dependency graph**,
resolved offline by `atomeBundletoolClasspath`; no second binary is downloaded.
Validation checks official bundle structure, package/version/SDK, release mode,
strict JDK/JAR signatures pinned to the upload certificate, native runtime/C++
payload, dynamic libc linkage, 16 KB ELF and bundle ZIP alignment, and SHA-256.
`apksigner` remains the APK verifier and is not used to verify an AAB.

Tests live in `tests/android/` and are registered in the Vitest manifest. Mocked
Google transactions prove client/recovery behavior; they do not prove access to
the owner's account. Actual first deployment must additionally verify:

- Play accepts the bundle, certificate, version, size and required declarations.
- An invited account installs from the **Play opt-in link**, not only through adb.
- A physical Android phone starts WebGPU/Bevy, responds to gestures and exercises
  supported account, project, media/audio and communication functions.
- The Play update N → N+1 preserves projects, media, preferences and sessions, and
  reloads the new bundled runtime. Derived asset extraction uses a content hash;
  it does not delete user data. Physical update acceptance is still required.

CI is optional and is not provisioned by this task. A future manually triggered
job must invoke this same generator and keep credentials outside its artifacts.
