## First indispensable missing capability — bounded proposal, not implementation

Component: shared configured-activity and result relations in the existing
Programme model. Need: one activity usable independently or linked to multiple
objectives, one calendar occurrence and one realized execution, with provenance,
corrections and references surviving project closure and reload.

Status: **Existing but unsuitable**. `PROGRAM_DEFINITIONS` contains Sleep and
Music; `PROGRAM_BRICKS` contains nap, meditation and nutrition strings.
`createProjectProgramRuntime` stores the plan in a project's `project_program`,
reads observations from that project and creates calendar events with that
project's `programLink`. The `two sleep instances and a musical instance remain
independent` test expects three separate event identities. The existing
programmes README and acceptance T22–T24 explicitly say shared instances/time
attribution are not finalized. These are inspected limitations, not inference
from filenames.

Investigation: Programme owners, first-launch and guided project consumers,
template assemblies, bootstrap tool definitions/handlers, core project/text/
calendar schemas, legacy Activities, health history, existing Programme tests
and documentation. Searches for `activity_id`, `objective_code`, `brick_id`,
shared project links, health records, vaccination and notebook terms across
eVe, Squirrel/shared sources and server found toolbox contexts but no verified
contract serving this need. Absolute absence elsewhere is not claimed.

Internal alternatives: template cloning preserves separate instances rather
than a single execution; calendar constraints compare projects but do not link
their activity identities; text observations are project-local; native health
history is a measurement reader, not the new configured-activity authority.

Proposed authorization: extend `project_program_model.js` and
`project_program_runtime.js`, and the existing shared Atome schema declarations,
for typed configured activities, explicit objective references, unique
occurrence/execution identity and append-only corrections. This includes an
explicit foundation-schema extension; no separate registry, database, transport,
mutation pipeline, renderer or dependency. Preserve current Sleep/Music objects
and consumers. Exact field/type choices remain subject to the verified existing
schema mechanisms; no undeclared property or speculative API is approved here.
Any separately necessary UI, health-notebook or networking brick has its own
bounded gate. First acceptance must demonstrate one activity, two objective
links, one realization, retry/reload, correction history and account isolation.
